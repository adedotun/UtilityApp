## What was built

### 1. Remove Blank Pages — `remove-blank-pages`, Organise, icon FileDashed
- `process.ts`: `analyzePage` calls a page blank when it has **no extractable text and** its rendered pixels are (near-)uniform. `inkRatio` measures the fraction of pixels differing from the page background by more than a channel threshold; the background is estimated from patches at the four corners, so an off-white scan is not mistaken for ink. Three sensitivities (strict 0.05% / normal 0.2% / loose 1% ink allowance) in `INK_LIMITS`. `detectBlankPages` takes an injected page renderer, following the OCR tool's deps pattern, so the browser supplies PDF.js + canvas and tests supply the Node canvas. Removal reuses `deletePages` from the Delete Pages tool.
- `Tool.tsx`: detection runs first, on demand, with a sensitivity select and per-page progress. Results show the detected pages in words (reusing Split's `describePageList`) plus the shared thumbnail grid with the blanks pre-selected for removal — the user can unselect any page to keep it, and the all-pages-selected trap is guarded exactly as in Delete Pages. Changing the file or sensitivity marks the detection stale and requires a fresh run. No blanks found is stated plainly.
- Tests: 7 (ink measurement on synthetic pixels including the exact 0.1% borderline that strict rejects and normal/loose accept, off-white background treated as background, text always defeating blankness; and the required fixture test: a 5-page PDF — text, empty, rectangle-only, empty, text — detects exactly pages 2 and 4 at all three sensitivities, the rectangle page is kept by its pixels despite having no text, and deleting the detected pages leaves a 3-page PDF with both text pages intact).

### 2. Compare PDFs — `compare-pdfs`, Organise, icon GitDiff
- `process.ts`: `extractPageLines` pulls each page's text via PDF.js (trimmed, blank lines dropped) and refuses a file with no readable text, naming which file and pointing at OCR. `diffLines` is a hand-rolled LCS line diff (no new dependency); past a million table cells it falls back to trimming the common head/tail and reporting the differing middle, which stays truthful. `comparePageTexts` classifies each position as same / changed / only-in-a / only-in-b, and `comparisonReport` renders the whole result as a plain-text file.
- `Tool.tsx`: the second PDF is picked inside Step 2 (the Insert Pages pattern). "Compare text" runs locally and shows summary counts, then a per-page list; changed pages expand to the line diff (− only in the first, + only in the second, capped at 60 lines on screen with the remainder noted). Step 3 saves the full text report. The notice states plainly that only text is compared — not layout, fonts or images — and that comparison is positional, page against page.
- Tests: 7 (LCS unit cases — change in place, insertion, deletion; page classification both directions; and the required fixture test: two 3-page PDFs differing only in page 2's text produce exactly one changed page whose diff is exactly the removed line "Bravo two" and the added line "Bravo two revised", with the report containing both; extra-page and no-text cases covered).

### 3. Grayscale PDF — `grayscale-pdf`, Optimise, icon CircleHalf
- `process.ts`: `grayscalePixels` converts an RGBA buffer in place using Rec. 709 luma, so R = G = B for every pixel; `buildGrayscalePdf` rebuilds from the renders through Compress's `buildRasterizedPdf`, reusing its level table (`LEVEL_DPI`) so quality/DPI options match Compress exactly. Deliberately no "return the original" guarantee: the point is the conversion, even if the file grows, and the UI says grayscale is not a size tool.
- `Tool.tsx`: mirrors the Compress tool — same three render levels, per-page progress and cancel — rendering each page, grayscaling its `ImageData`, and re-encoding as JPEG. The notice states the pages become images and text stops being selectable, with a pointer to OCR for a searchable copy.
- Tests: 3 (exact luminance values for the primaries with alpha preserved; empty render list rejected; and the required end-to-end test: a 2-page fixture with red and blue rectangles is rendered, grayscaled and rebuilt, and the output's rendered pages sample R = G = B within JPEG tolerance at the expected luminance, with the page count unchanged).

### 4. Split by Bookmarks or Size — `split-by-bookmarks`, Organise, icon BookmarkSimple
- Bookmarks mode: `readOutline` uses PDF.js `getOutline`, resolving named and explicit destinations to 1-based pages (top level only; external links skipped). `chaptersFromOutline` sorts entries, collapses duplicates on one page, spans each chapter to the page before the next, and makes pages before the first bookmark a leading file of their own so nothing is dropped or silently merged. Files are produced by Split's `splitPdfGroups` and renamed `01-chapter-title.pdf` style via `chapterFileName`. A PDF with no outline gets the honest error, with Split by ranges named as the alternative.
- Size mode: `estimatePageSizes` is render-free — per page it sums the page's content-stream bytes plus its referenced image-stream bytes, then adds an even share of everything else in the file (fonts, structure); the method is documented in the code and in the UI copy. `planSizeSplit` packs pages in order under the target; a single page over target always forms its own file. After splitting, the real output sizes are checked and the result reports oversized single-page files (and any other file that came out over) by name.
- `Tool.tsx`: a mode select (Bookmarks / File size), a target-size input in MB with inline range validation (0.05–500 MB), and copy that explains both modes and the estimation caveat before anything runs. Outputs arrive as the multi-file download list, like Split.
- Tests: 13 (chapter spanning, leading-pages chapter, sorting/dedup/out-of-range on synthetic outlines; file-name slugging; size packing including the exact-fit boundary and the oversized-single rule; estimates positive and summing to the file size; and the required real-fixture tests: a 6-page PDF with a genuine outline — hand-built with pdf-lib's low-level objects, since pdf-lib has no outline API — reads back as Intro/Middle/End at pages 1/3/5 and splits into three correctly named 2-page files; a no-outline PDF is refused plainly; a noisy-image page over the smallest target produces exactly one file and exactly one oversized-single warning).

### 5. Fill Form — `fill-form`, Edit and sign, icon ListChecks
- `process.ts`: `listFormFields` describes every AcroForm field via pdf-lib — text (with multiline flag), checkbox, dropdown, radio group, option list — with current values and choice options; button and signature fields are reported as not fillable rather than hidden. `fillForm` writes values back with choice fields validated against their own options (a bad value fails naming the field), supports flatten-after-filling, and refuses to save when nothing was filled. XFA is detected from the AcroForm dictionary — **before** calling `getForm()`, because pdf-lib's `getForm()` deletes the XFA entry on first access (found in pdf-lib's source during this wave and verified by experiment); checking afterwards would always report false.
- `Tool.tsx`: fields load when the file is added (the Excel preview's keyed-state pattern) and Step 2 renders one input per field — text input or textarea for multiline, checkbox, select for choice fields — labelled by field name, with a changed-field count gating Step 3. No-fields and XFA-only forms each get their own plain message (XFA points at desktop readers); a form carrying both AcroForm fields and XFA data says the standard fields are the fillable ones. Unfillable fields are listed by name, with a pointer to Sign PDF for signatures.
- Tests: 8 (field description for all four fillable types with options; a formless PDF reporting no fields and no XFA; the required fill test: a pdf-lib-built form fixture — text field, checkbox, dropdown, radio — filled through `fillForm` reads back exactly the written values, flatten leaves zero fields, an invalid choice and an unknown field name are rejected by name, and saving with nothing filled is refused; XFA detection verified against a genuine XFA-carrying file built by appending an incremental update to a pdf-lib file, since pdf-lib strips XFA from anything it saves).

### 6. Booklet — `booklet-pdf`, Organise, icon BookOpen
- `process.ts`: `bookletSides` is the imposition Wave 3a deliberately left out of N-up: pad to a multiple of four, then each sheet's front pairs the last remaining page (left) with the first (right) and its back pairs the second (left) with the second-to-last (right). `bookletPdf` embeds the pages once each and draws them scaled-to-fit, centred, two per landscape A4/Letter sheet (sheet constants reused from N-up), leaving padding halves empty. The result reports sheet and side counts and how many blanks were padded.
- `Tool.tsx`: sheet-size select, a live count of sheets and padding blanks for the loaded document, and plain printing instructions (double-sided, flip on the short edge, fold the stack in half).
- Tests: 7 (padding counts; the exact side order for 8 and 4 pages; every padded page used exactly once for several lengths; and the required fixture test: an 8-page document yields 2 landscape A4 sheets / 4 sides, and PDF.js text positions on side 1 put "Page 8" in the left half and "Page 1" in the right half, with side 2 holding pages 2 and 7 the same way; a 5-page document pads 3 blanks, reports them, and its first side carries only page 1, on the right).

## Left unresolved / notes for later waves

- **Ring 1 is complete.** Every row of roadmap §4 now has a shipped, tested tool. The remaining roadmap work is Ring 2 (batch mode, workers, workflows — Playwright end-to-end tests still outstanding from the rebuild) and Ring 3 (beyond PDF), plus the FileTweaks rename decision in §9 of the roadmap.
- **XFA fixture method:** pdf-lib strips XFA from any document it saves, so the XFA test fixture is a real file assembled by appending a standard incremental update to a pdf-lib-written form. Detection itself was verified through the exact path the tool uses (`PDFDocument.load` → AcroForm dictionary, checked before `getForm()` can delete it).
- **Node rendering of vector pages** needs a global `Path2D`, which browsers have natively; the new tests install the Node canvas package's `Path2D` as a test-only polyfill, alongside the existing `toHex`/upsert polyfills. No production code is affected.
- **Compare PDFs is positional** (page N against page N) by design and says so in its notice; a moved page shows as changed in both positions. Content-based page matching would be a different, larger tool.
- **Size-mode estimates** can misjudge pages whose large images are shared with other pages (the shared bytes are spread evenly). The post-split size check and the named oversized-file warnings in the result are the honesty backstop, and the UI copy describes sizes as estimated.
- As with Waves 1–3a, the six new tools were verified through the Node test path (the same engine code the browser runs); a live smoke check of the six new routes after the next deploy is still worth doing, like the password-tools live check in the rebuild.
